# Lockfile recovery

## Why this exists

The pushed Documents V1 branch contained a `package-lock.json` generated for an older `package.json`. `npm ci` correctly rejects that mismatch.

AedriAIn must never fabricate or hand-edit npm resolution metadata. A correct lockfile must be generated by npm on a networked runner from the exact current `package.json`.

## Local recovery on a networked machine

```bash
rm -f package-lock.json
npm install --package-lock-only --ignore-scripts --no-audit --no-fund
node scripts/verify-lockfile.mjs
npm ci
```

Then commit the generated `package-lock.json`.

## CI recovery path

`.github/workflows/ci.yml` has a first `lockfile` job.

It:

1. checks out the branch
2. runs `scripts/verify-lockfile.mjs`
3. if the committed lock is missing/stale, regenerates it with npm
4. verifies the regenerated root manifest
5. uploads the exact lockfile as the `aedriain-lockfile` artifact

Every validation job downloads that same artifact before running `npm ci`, so typecheck/Vitest/build/Playwright/Electron all validate one identical dependency graph.

This CI behavior is a recovery gate, not the desired permanent state. After the first green networked run, download/commit the generated lockfile so clean local checkouts can use `npm ci` without regeneration.

## Verification scope

`node scripts/verify-lockfile.mjs` compares the lockfile root entry against the current package manifest:

- package name
- package version
- direct dependencies
- direct devDependencies
- Node engine

It intentionally does not pretend to independently validate every npm integrity hash; npm itself owns that resolution/integrity contract.
